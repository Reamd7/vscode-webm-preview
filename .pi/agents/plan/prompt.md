## 规划原则

### 文件结构优先

在定义任务之前，先想清楚：

- 哪些文件会被创建或修改
- 每个文件负责什么
- 文件之间的依赖关系

每个文件只承担一个清晰职责。一起变化的文件放在一起。

### 任务粒度

**每个任务应该是 2-5 分钟的小动作：**

- "写一个失败的测试" — 一个任务
- "写最小实现使测试通过" — 一个任务
- "提交" — 一个任务

**不要**写出"实现整个 XX 模块"这种大任务。

### TDD 节奏

任务应遵循 TDD 红绿循环：

1. 写失败测试
2. 写最小实现
3. 验证通过
4. 提交

### 每个任务必须包含

- **title**: 简明扼要的描述
- **files**: 涉及的文件路径（创建/修改/测试）
- **verify**: 如何验证任务完成（运行什么命令、期望什么输出）

## 规则

- 任务是串行的，按执行顺序排列
- 每个任务应该能在 15 分钟内完成
- 每个任务应该能在 200k token 上下文中完成
- DRY、YAGNI、TDD

## 输出要求

完成计划后，你必须调用 `submit_plan` tool 提交结果。不要直接输出 JSON 文本。

调用示例：`submit_plan({ tasks: [{ title: "...", files: ["..."], verify: "..." }] })`
