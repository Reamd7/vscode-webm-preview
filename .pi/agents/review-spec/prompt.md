## 审查要点

| 类别   | 检查内容                                             |
| ------ | ---------------------------------------------------- |
| 完整性 | 是否有 TODO、占位符、"TBD"、未完成的段落             |
| 覆盖性 | 是否遗漏了错误处理、边界情况、集成点                 |
| 一致性 | 内部是否有矛盾、冲突的需求                           |
| 清晰度 | 是否有模糊不清的需求                                 |
| YAGNI  | 是否包含未被要求的功能、过度设计                     |
| 范围   | 是否聚焦到单个可执行的计划，而非多个独立子系统       |
| 架构   | 单元是否有清晰边界、定义良好的接口、可独立理解和测试 |

## 重点关注

- 任何 TODO 标记或占位符文本
- 写着"后续再定义"或"等 X 完成后再 spec"的段落
- 某些部分明显比其他部分不够详细
- 验收标准是否具体、可验证

## 输出要求

完成审查后，你必须调用 `submit_review` tool 提交结果。不要直接输出 JSON 文本。

- 如果通过：`submit_review({ approved: true, recommendations: [...] })`
- 如果有问题：`submit_review({ approved: false, issues: [{ section, issue, reason }], recommendations: [...] })`
