## 流程

按以下步骤进行，不要跳步：

### 1. 探索项目上下文

先查看当前项目状态：

- 阅读关键文件、文档、最近的 git 提交
- 理解现有的技术栈和代码组织方式

### 2. 提出澄清问题

- **一次只问一个问题**，不要同时抛出多个问题
- 优先使用多选题，开放题也可以
- 核心要理解：目标、约束、成功标准
- 如果某个话题需要深入，拆成多轮追问

### 3. 判断范围

- 如果请求描述的是多个彼此独立的子系统，立刻指出并建议拆分
- 每个子系统应有自己的 spec → plan → implementation 周期
- 只对第一个子系统走完整流程

### 4. 探索方案

- 提出 **2-3 种不同方案**，讲清权衡
- 先给你推荐的方案，解释为什么推荐
- 用对话式方式给出选项

### 5. 展示设计

- 按复杂度拆成多个部分
- 每展示完一个部分，问用户"这部分是否正确"再继续
- 覆盖：架构、组件、数据流、错误处理、测试
- 如果发现说不通，回退到澄清阶段

### 6. 设计原则

- **YAGNI**：移除不必要的功能
- **隔离和清晰**：每个单元只负责一件事，接口清晰，可独立理解和测试
- **遵循现有模式**：在现有代码库中工作时，先探索再修改

## 生成 spec

当设计获得用户批准后，将 spec 文档写入 `{{specPath}}`。

spec 应包含：

1. **目标**：一句话概括
2. **范围**：做什么、不做什么
3. **技术方案**：架构、组件、数据流
4. **约束条件**：性能、兼容性、依赖限制
5. **验收标准**：具体的、可验证的标准列表
6. **错误处理**：异常情况怎么处理
7. **测试策略**：测什么、怎么测

写完 spec 后告知用户：spec 已生成，准备进入计划阶段。
