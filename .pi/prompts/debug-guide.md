# 系统化调试指导

你已经在这个任务的修复循环中多次失败了。**停止随机修补，开始系统化调试。**

## 铁律

```
在先完成根因调查之前，不允许提出任何修复方案。
```

## 四个阶段（必须按顺序）

### 第一阶段：根因调查

1. **认真阅读错误信息** — 不要跳过。Stack trace 从头到尾读完。记下行号、文件路径、错误码。
2. **稳定复现问题** — 精确步骤是什么？每次都会发生吗？
3. **检查最近的变更** — `git diff`、最近提交、新依赖、配置变更
4. **追踪数据流** — 错误值从哪里来？谁把坏值传到这里？一直向上追直到源头。**在源头修，不在症状位置修。**

### 第二阶段：模式分析

1. **找出正常工作的例子** — 代码库中类似且正常的代码
2. **对比差异** — 正常版本和损坏版本的每个差异都列出来
3. **理解依赖** — 需要什么配置、环境、前置条件？

### 第三阶段：假设与验证

1. **一次只提一个假设** — 写下来："我认为 X 是根因，因为 Y"
2. **最小化验证** — 一次只改一个变量
3. **验证后再继续** — 没成功就提新假设。**不要在失败修复上叠更多修复。**

### 第四阶段：实施修复

1. **先写失败测试** — 用 TDD 复现 bug
2. **单一修复** — 只针对根因，一次一个改动
3. **验证** — 测试通过？其他测试没坏？

## 红旗（出现就停下回到第一阶段）

- "先快速修一下，之后再调查"
- "先改个 X 试试看能不能行"
- "多改几个地方，再跑测试看看"
- "我还没完全理解，但这个可能能行"

## 防御性编程

修复 bug 后，在数据流经过的每一层都加入验证：

- **入口验证** — 拒绝无效输入
- **业务逻辑验证** — 数据对这个操作是否合理
- **环境守卫** — 防止特定上下文下的危险操作
- **调试日志** — 记录关键操作的上下文
