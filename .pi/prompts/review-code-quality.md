## 审查要点

### 代码结构

- 每个文件是否只有一个清晰职责？
- 单元是否可以被独立理解和测试？
- 接口是否清晰、边界是否明确？

### 命名和可读性

- 命名是否清晰准确（描述做什么，而非怎么做）？
- 代码是否易于阅读和理解？

### 测试质量

- 测试是否验证行为（而非 mock 行为）？
- 是否遵循了 TDD（先测试后实现）？
- 边界情况和错误情况是否覆盖？
- 测试是否最小化（每个测试只测一件事）？

### 测试反模式检查（重点）

- **是否测试了 mock 行为？** — 断言中是否检查了 mock 元素的存在而非真实组件行为？如果 assert 的目标带有 `mock` 字样或只验证 mock 被调用，则为反模式。
- **是否有仅测试用的生产方法？** — 生产代码中是否有只被测试文件调用的方法？应移到测试工具中。
- **mock 是否完整？** — mock 的数据结构是否包含了真实 API 返回的所有字段？部分 mock 会在下游代码访问缺失字段时静默失败。
- **是否过度 mock？** — mock setup 是否超过测试逻辑的 50%？是否可以用真实组件替代？
- **mock 前是否理解了依赖？** — 被 mock 的方法是否有测试依赖的副作用？如果有，应在更低层级 mock。

### 防御性编程检查

- 关键数据流是否有多层验证（入口校验 + 业务逻辑校验），而非只在一个点做检查？
- 是否对无效输入有明确的错误处理（而非静默忽略或传递）？
- 错误信息是否包含足够的上下文（哪个值、从哪来、期望什么）？

### 设计质量

- 是否遵循 YAGNI（没有过度设计）？
- 是否遵循 DRY（没有不必要的重复）？
- 是否遵循现有代码库的模式？

## 输出要求

你必须输出一个 JSON 对象（不要用 markdown 代码块包裹）：

{
"approved": true/false,
"strengths": ["做得好的方面"],
"issues": [
{ "severity": "critical/important/minor", "description": "具体问题", "file": "文件路径" }
]
}

- critical：必须修复才能通过（bug、安全问题、测试反模式）
- important：应该修复（缺少防御性校验、架构问题）
- minor：建议改进（命名、风格）

只有存在 critical 或 important 问题时，approved 才为 false。

只输出 JSON，不要其他文本。
